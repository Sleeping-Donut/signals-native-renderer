# 07 — Retained Renderer

**Crate:** `renderer-native` (the outline called this `renderer-gpui`)
**Depends on:** `view`, `layout`, `text`, `platform`
**Owns:** the retained view tree, node bindings, structural updates, paint
caches, scene replay, and the first-party render path.

---

## 1. The central choice

There are three plausible models for a signal-driven native renderer.

### Model A — GPUI's model

- Retained: view entities (`Entity<V>`) and their state.
- Ephemeral: the element tree is rebuilt every frame by `Render::render`.
- Incremental: each view's prepaint/paint phases are cached by a
  `ViewElementState`; if the view was not notified and the bounds/style/key are
  unchanged, the cached ranges are replayed (`refs/zed/crates/gpui/src/view.rs`).

**Strengths:** proven at scale, simple ownership, functional composition,
per-view caching is a strong granularity, and the element tree can be thrown away.
**Weaknesses:** a single changed signal re-renders the entire view subtree that
read it; fine-grained updates require splitting views or bindings manually.

### Model B — fully retained nodes, one binding per property

- Retained: every element and text node.
- Dynamic values: each property is an effect that writes the node in place.
- Structure: conditionals and lists are explicit nodes with their own effects.

**Strengths:** maximum granularity; no per-frame tree; ideal fit for signals.
**Weaknesses:** component functions become "build once, bind forever"; writing a
binding for every property is verbose; structural updates are the hard part.

### Model C — chosen: retained nodes with dynamic view slots

- Retained: view nodes and their child structure, built at mount.
- Dynamic values: bindings (effects) for the properties that actually change.
- Structure: `Show`, `For`, and keyed lists are explicit control-flow nodes with
  their own bindings.
- Escape hatch: a `Dynamic` view slot replaces one child subtree under a stable
  host when its key changes. `Rebuild` is sugar over it. Use it when binding
  overhead exceeds replacement cost (e.g. a settings form with many
  interdependent fields).

Model C gives signal-level granularity by default and keeps Model A's simplicity
where it is the better tool. It is the only model that satisfies both "one
signal write updates one text run" and "a component can be a function that
returns a tree".

## 2. View node model

```rust
pub struct ViewNode {
    pub id: ViewNodeId,
    pub parent: Option<ViewNodeId>,
    pub first_child: Option<ViewNodeId>,
    pub last_child: Option<ViewNodeId>,
    pub next_sibling: Option<ViewNodeId>,
    pub prev_sibling: Option<ViewNodeId>,

    pub kind: ViewKind,
    pub style: Style,
    pub layout: LayoutState,
    pub paint: PaintCache,
    pub bindings: SmallVec<[Binding; 4]>,
    pub flags: ViewFlags,
    pub owner: OwnerId,
}

pub enum ViewKind {
    Element { tag: Tag },
    Text { content: String },
    Fragment,
    Component { type_id: TypeId },
    Conditional { active: Option<ViewNodeId> },
    KeyedList { key_map: HashMap<Key, ViewNodeId> },
    Overlay { layer: Layer },
    Portal,
}

bitflags! {
    pub struct ViewFlags: u32 {
        const NEEDS_STYLE   = 1 << 0;
        const NEEDS_LAYOUT  = 1 << 1;
        const NEEDS_PAINT   = 1 << 2;
        const NEEDS_CHILDREN= 1 << 3;
        const NEEDS_A11Y    = 1 << 4;
        const HIDDEN        = 1 << 5;
        const DISPOSED      = 1 << 6;
    }
}
```

Why sibling links rather than `Vec<ViewNodeId>`:

- O(1) insert/remove in a keyed list reorder;
- stable order independent of allocation;
- no `Vec::splice` shifting;
- easy to move a node between parents (rare, but needed for portals).

Iteration is a linked-list walk. For paint and layout, a contiguous child order is
useful; `scene_build` can collect a `SmallVec` per parent, or the node can cache a
`ChildOrder` vector rebuilt on structural change. Start with links; add a
flattened index if profiling shows a problem.

## 3. Bindings

A binding is an effect that writes one property:

```rust
pub struct Binding {
    pub effect: EffectHandle,
    pub target: BindingTarget,
}

pub enum BindingTarget {
    Text,
    Attr(AttrId),
    Style(StyleFieldId),
    Visibility,
    ChildRange { key: ChildKey },
    A11y(A11yField),
}
```

Example generated by `view!`:

```rust
// view! { <div>{count}</div> }
let text = cx.create_text("");
let effect = render_effect(
    cx,
    move || count.get(),                // compute: tracked
    move |value| tree.set_text(text, value.to_string()), // apply
);
tree.add_binding(text, effect);
```

`set_text` marks the text node `NEEDS_PAINT` and propagates to its ancestors up
to the nearest paint root (usually the window; later, a layer). Text does not
mark layout unless the text is measured as part of layout (it is, if the text
node has an intrinsic size). In that case the binding marks `NEEDS_LAYOUT` too.
The binding knows which because the text node's style has `auto` width/height.

### 3.1 Binding granularity

One binding per dynamic expression, not per node:

- `{count}` → one text binding;
- `{format!("{first} {last}")}` → one binding that reads both signals;
- `class:selected=is_selected()` → one attribute binding;
- `style:width=width()` → one style binding;
- `when(cond, ...)` → one conditional binding (structure);
- `for item in items` → one list binding.

A binding's compute function should read only the signals it needs. The `view!`
macro compiles expressions directly; it does not wrap the whole node in a
rebuild.

### 3.2 Applying bindings

Bindings apply in creation order after the compute heap. An apply must be
idempotent and must not read reactive values (the compute half already captured
them). If an apply needs to read another signal, it should be part of the compute
function, not the apply.

## 4. Mounting

A component mount:

1. Creates an owner.
2. Creates a component state value (`Self` or a generated state struct).
3. Runs the body with the owner current.
4. The body calls builder functions that create view nodes and bindings.
5. The returned root `ViewNodeId` is inserted into the parent.

The body runs **once**. A plain signal read in the body is untracked and does
not subscribe (in dev, a warning: `STRICT_READ_IN_MOUNT`). To read a value at
mount, use `untrack(|| ...)` or read it in a binding.

This is the biggest mental-model change from Solid/Leptos/GPUI:

> A component is a mount function, not a render function.

Why:

- It matches the fine-grained graph: there is no reason to re-run structure when
  only a text value changed.
- It makes retained identity natural: nodes are created once and kept.
- It makes structural updates explicit: `Show`/`For` are the only nodes that
  add/remove children.

### 4.1 Dynamic view slots

```rust
Dynamic::new(
    key,
    move || view! { <SettingsForm state=state /> },
)
```

A `Dynamic` node is a stable host whose one active child is replaced when the key
changes. It is the primitive behind "recompute this subtree from state".
`Rebuild::new(closure)` is sugar for a `Dynamic` keyed on the closure's tracked
reads. Use it when:

- the structure is highly dynamic (many conditionals);
- the subtree is cheap to build;
- binding every property would be more code than replacing the subtree;
- the component is a leaf with no important local state.

Solid and Leptos do not need a special rebuild component: `<Show>`, `<Switch>`,
`<Dynamic>`, and function children already replace subtrees. `Dynamic` is our
equivalent. It disposes the old child owner and mounts a new one under the same
host. Focus/scroll is lost unless state is hoisted or `KeepAlive` is used.

### 4.2 Props

Props are uniform `Prop<T>` values, never bare `T` when they might change:

```rust
pub enum Prop<T> {
    Static(T),
    Reactive(Signal<T>),
    Derived(Memo<T>),
}

#[derive(Clone)]
pub struct CounterProps {
    pub label: Prop<String>,
    pub count: Prop<i32>,
}

#[component]
fn Counter(props: CounterProps) -> impl View {
    view! {
        <div>
            <span>{props.label}</span>
            <span>{props.count}</span>
        </div>
    }
}
```

Reading a `Prop<T>` is uniform: `.get()` / `.with()` returns the static value or
reads the signal/memo. A `Prop::Static` allocates no graph node and creates no
edge; `Reactive`/`Derived` subscribe normally.

Props are never bare `T` when they can change. `Prop<T>` removes the trap: a
component signature cannot accidentally accept a snapshot and silently stop
updating. The macro maps `<Counter count=count />` to `Prop::Reactive(count)`,
`<Counter count=0 />` to `Prop::Static(0)`, and `<Counter count=move || ... />`
to `Prop::Derived(memo)`.

Prop updates:

- If the parent passes a stable signal/memo handle, the child reads it directly;
  no update path is needed.
- If the parent's expression changes identity (e.g. a new `Memo` per mount), the
  child must be replaced or the prop signal must be updated. Prefer stable
  handles.
- A `Static` prop never updates; that is explicit and zero-cost.

## 5. Structure: conditionals

`Show` is a view node with one active child:

```rust
pub struct Conditional {
    pub condition: Memo<bool>,
    pub active: Option<ViewNodeId>,
    pub then_branch: Box<dyn Fn(&mut Cx) -> ViewNodeId>,
    pub else_branch: Option<Box<dyn Fn(&mut Cx) -> ViewNodeId>>,
}
```

The condition has a binding. On change:

- if the truthiness flips, dispose the active branch's owner and mount the other;
- if it stays the same, no structural work.

The node itself remains, so its position and style (e.g. a wrapper) are stable.
A `Match`/`Switch` node generalizes this to keyed branches; only the active
branch is mounted.

`KeepAlive` (v1.1) moves the inactive branch's owner to a cache and re-inserts
it on return, preserving state.

## 6. Structure: keyed lists

A `For` node owns:

```rust
pub struct KeyedList<Item, Key> {
    pub items: Memo<Vec<Item>>,
    pub key_fn: Box<dyn Fn(&Item) -> Key>,
    pub rows: HashMap<Key, ViewNodeId>,
    pub order: Vec<Key>,          // committed order
    pub row_factory: Box<dyn Fn(Key, &Item, &mut Cx) -> ViewNodeId>,
}
```

On update:

1. Compute the new key sequence.
2. Walk old and new sequences with a keyed diff:
   - same key at the same position: keep the row;
   - key moved: unlink and re-insert before its new successor;
   - key removed: dispose the row owner;
   - key added: mount a new row.
3. Update `order`; mark `NEEDS_CHILDREN` and `NEEDS_LAYOUT`.
4. Only rows whose item value changed re-run their item binding. Row identity
   (focus, scroll, local signals) is preserved across moves.

The diff algorithm: build a `HashMap<Key, usize>` of old positions, then walk the
new sequence with a cursor into the old linked list. For each new key:

- if the old node is already before the cursor, it moved left: unlink and insert
  before the cursor;
- if it is after, advance the cursor past nodes that are not in the new set
  (they will be removed) and insert;
- if absent, mount.

This is O(n) expected time. The number of tree moves is the number of rows not in
the longest increasing subsequence of old positions, which is minimal for a
keyed reorder. It is the same shape Solid's `mapArray` and Leptos' keyed diff use.

This is **not** a virtual-DOM diff. It does not compare element descriptions or
rebuild node trees; it compares stable keys and moves existing nodes. The only
thing that changes is sibling order.

Why not index-based diff: index diff destroys row state on a prepend, which is
the most common list operation (chat, logs). Keyed identity is non-negotiable for
a retained renderer.

### 6.1 Virtualization

`VirtualList` is a list node that mounts only visible rows plus an overdraw
window:

- owns a `ScrollState` (offset, viewport, item sizes);
- computes the visible key range from cumulative sizes;
- mounts rows in that range, disposes rows outside;
- keeps a key → row map for visible rows only;
- uses a size cache for off-screen rows (uniform height or measured heights).

Virtualization is a rendering concern, not a reactive one. The item list is a
`Memo<Vec<Item>>`; the virtual list reads the slice it needs inside the row
factory. It must not subscribe every row to the whole list.

GPUI's `List`/`UniformList` are the reference for scroll anchoring and
measurement (`refs/zed/crates/gpui/src/elements/list.rs`,
`uniform_list.rs`). Our retained list can keep `ScrollState` on the node rather
than in an external `ListState`, which removes the GPUI requirement that the
view hold list state.

## 7. Dirty propagation

Dirty flags flow **up**, not down:

- A binding marks its node `NEEDS_PAINT` and its ancestors `NEEDS_PAINT` up to
  the nearest paint root (window/layer).
- A layout-affecting change marks `NEEDS_LAYOUT` and `NEEDS_PAINT` up to the
  nearest layout root (a fixed-size/contained ancestor, or the window).
- A structural change marks `NEEDS_CHILDREN` and `NEEDS_LAYOUT`.
- A text change marks `NEEDS_PAINT`; if the text node has intrinsic sizing, it
  also marks `NEEDS_LAYOUT`.

The runtime collects the highest dirty roots per phase and processes only those
subtrees. It does not walk the whole tree to find dirty nodes.

Why up: a child's change affects the parent's paint range (the parent replays
children), and possibly its layout. Propagating up is cheap (path to root) and
lets each phase start from a small root set.

### 7.1 Memory profile

View nodes are the dominant framework memory term (roughly 0.7–1.1 KB each
before optimization). The resolved `Style` is the largest field. Two levers:

- **Intern resolved styles.** Most nodes share a small set of styles; store a
  `StyleId` into a global table instead of a full struct per node. This can cut
  the per-node cost by 30–50%.
- **Avoid inline bindings for static nodes.** Use a boxed slice or an
  `Option<Box<[Binding]>>`; a node with no bindings should not pay for four
  inline slots.

Measure before changing the representation; the node is on the hot path and a
smaller struct is not automatically faster if it adds an indirection.

## 8. Paint cache and scene replay

Each node stores the range of primitives it emitted in the previous scene:

```rust
pub struct PaintCache {
    pub range: Range<u32>,       // into the previous scene's ops
    pub bounds: Bounds<Px>,
    pub layer: LayerId,
    pub valid: bool,
}
```

Scene build:

```
fn build(node):
    if !node.dirty_paint && node.paint.valid:
        scene.replay(prev_scene, node.paint.range)
        return
    let start = scene.len()
    emit own primitives
    for child in children: build(child)
    node.paint.range = start..scene.len()
```

This is GPUI's `Scene::replay` pattern
(`refs/zed/crates/gpui/src/scene.rs`). It avoids re-emitting unchanged subtrees
and makes paint cost proportional to the dirty set.

Important: replay must reproduce exactly what a full rebuild would emit. This is
invariant I9 and the basis of the differential test: build a scene fully, build
it incrementally after a change, assert equal.

### 8.1 Damage regions

The scene builder can union the bounds of dirty nodes into a `Damage` list. The
backend may:

- redraw the whole surface (v1, simplest);
- scissor to damage rects and blend (v2);
- keep a texture atlas and update only damaged tiles.

**What wgpu can and cannot do.** Retained-mode partial work splits into three
layers:

1. **Scene/paint replay** — pure CPU; wgpu is irrelevant. Clean nodes replay
   their ranges and dirty nodes re-emit. This works fully.
2. **GPU draw work** — wgpu supports `RenderPass` with scissor/viewport and
   `LoadOp::Load`, so you can redraw only damage rects into a **texture you own
   across frames**. Do not rely on the swapchain image retaining its previous
   contents; acquire/present may rotate or discard it. The usual pattern is an
   offscreen retained color target, draw damage rects into it, then blit/present
   the whole target.
3. **True partial present** — platform APIs such as Metal
   `presentWithDamage`, DXGI `Present1` dirty rects, or Wayland surface damage.
   wgpu does not expose portable damage/present regions. That requires a native
   backend or a platform extension.

So: retained-mode **scene and command** partial updates work with wgpu. Partial
**fragment work** works with an offscreen retained target plus scissor. Partial
**present bandwidth** does not, portably. v1 presents the whole scene; v2 can add
the offscreen retained target and damage scissoring; v3 can add a native backend
for true partial present if power/bandwidth measurements justify it.

GPUI presents the whole scene; partial present is a later optimization.

## 9. Invalidation and `notify`

There is no manual `notify()` for state. A signal write marks its bindings. But
two things still need explicit notification:

1. **External state change** (e.g. a platform theme change) that is not a
   signal. Wrap it in a signal: `theme.set(...)`. The framework does not have a
   side channel.
2. **A dynamic view slot** keyed on non-reactive data. Put that data in a
   signal and let the slot's key change, or call `cx.request_rebuild(host_id)` to
   schedule a replacement for the next apply phase.

This is a deliberate removal of GPUI's `cx.notify()`: if a value affects the
view, it should be a signal. `notify` becomes a diagnostic escape hatch, not the
primary invalidation path.

## 10. View state and identity

Persistent state (scroll offset, focus, selection, hover, local signals) belongs
to:

- the component's owner/state struct for component-local state;
- the view node for element state (`ScrollState`, `FocusHandle`);
- a `KeyedList` row owner for row-local state.

Identity rules:

- A view node's `ViewNodeId` is stable from mount to removal.
- A keyed row keeps its node across reorder.
- A conditional branch gets a new node when remounted (unless `KeepAlive`).
- A rebuild replaces the subtree's nodes; state stored outside survives.

Accessibility node IDs derive from `ViewNodeId` + a path hash, so they are stable
across frames and across reorder (a keyed row keeps its ID). This is an advantage
over GPUI's `GlobalElementId` path hash, which changes when a keyed row's sibling
order changes.

## 11. Example

```rust
#[derive(Clone, Store, Patch)]
struct AppState {
    new_title: String,
    todos: Vec<Todo>,
}

#[derive(Clone, Store, Patch)]
struct Todo { id: u64, title: String, done: bool }

#[component]
fn App(state: Store<AppState>) -> impl View {
    let filter = Signal::new(Filter::All);

    view! {
        <div class="app">
            <Header title="Todos" />
            <input
                value=state.new_title()
                on_input=move |cx, text| state.new_title().set(text)
            />
            <button on_click=move |cx| {
                let id = next_id();
                let title = state.new_title().get();
                state.new_title().set(String::new());
                state.todos().push(Todo { id, title, done: false });
            }>"Add"</button>

            <Show when=move || state.todos().len().get() > 0
                  fallback=|| view! { <Empty /> }>
                <For each=state.todos()
                     key=|todo| todo.id
                     children=|todo| view! {
                         <Row todo=todo.clone() />
                     } />
            </Show>
        </div>
    }
}

#[component]
fn Row(todo: Field<Todo>) -> impl View {
    view! {
        <div class="row">
            <input type="checkbox" checked=todo.done() />
            <span>{todo.title()}</span>
        </div>
    }
}
```

Compiled shape (simplified):

- `div.app` is an element node with a style binding and a child list.
- `Header` mounts once.
- `input.value` is an attribute binding; `on_input` is an event listener.
- `button.on_click` is an event listener that pushes to the store.
- `Show` is a conditional node with a len binding.
- `For` is a keyed list node with a keyed memo.
- `Row` mounts once per key; `todo.done()` and `todo.title()` are bindings.

## 12. Tests

- **Mount once**: a component body runs exactly once across 10k updates; its
  bindings run according to their deps.
- **Binding granularity**: changing `first` updates the `first` text binding and
  not the `last` binding.
- **Structure**: `Show` flips dispose/mount branches; no leaked owners.
- **Keyed list**: prepend/move/remove preserve row state and focus; only changed
  rows run bindings.
- **Paint replay**: full rebuild vs incremental produce identical scenes after
  random edits (differential test).
- **Dirty propagation**: a paint-only change does not mark layout; a text change
  with intrinsic width marks both.
- **Dynamic slot**: subtree replaced under the same host; parent bindings
  survive; old owner disposed.
- **Identity**: keyed row ID survives reorder; accessibility ID stable.
- **Allocation**: a paint-only update allocates zero in steady state.
- **Fuzz**: random tree edits + random signal writes; invariants I7–I9 hold;
  no orphan nodes.

## 13. Open questions

1. **Default view-slot granularity.** Is mount-once too surprising for users coming
   from React/Solid? The `view!` macro can make bindings transparent, so the
   answer is mostly documentation and diagnostics.
2. **Component-local state.** A `struct Counter { count: Signal<i32> }` per mount,
   or a closure-captured signal? Both work; the macro should pick one and hide
   it.
3. **Child order representation.** Linked list vs cached `Vec` per parent. Start
   with links; measure.
4. **Text intrinsic sizing.** Does a text node's width depend on its content
   (auto) by default? If yes, every text change is a layout change. Consider
   defaulting text to `width: max-content` with an explicit `wrap` opt-in, or
   cache measured widths.
5. **Paint roots.** A window is the natural root; layers (overlays, tooltips) are
   separate roots. How do we scope damage to a layer?
6. **KeepAlive.** Is it needed in v1? Tabs and navigation state are common; maybe
   a `KeepAlive` wrapper in v1.1.
